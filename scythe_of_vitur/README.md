# Scythe of Vitur — backport from OSRS to LostCity rev 254

A Theatre of Blood weapon (OSRS obj 22325), backported straight from
`cache.osrs239` with `3draster/3rd/rscache/tools/port_lostcity` and its
manifest `port_lostcity/scythe_of_vitur.ini`. See `ghrazi_rapier/README.md`
(same session, same method) for the companion item.

## No LostCity reference

This content tree preserves 7 September 2004, fifteen years before Theatre of
Blood existed. `grep -ril vitur LostCity_Server/content` finds nothing but
this port's own files. The one thing the tree already had is the generic
`weapon_scythe` category — a style table (`combat.dbrow`) and the defensive
spin case in `skill_combat/scripts/combat.rs2` — which this item reuses for
its base stats, but which says nothing about hitting more than one target.
That is the whole of what is "content there" for this item; the cleave itself
is authored fresh.

To redo or re-derive this export: from the `3draster` repo root,
```
./3rd/rscache/tools/port_lostcity/port_lostcity \
  --manifest 3rd/rscache/tools/port_lostcity/scythe_of_vitur.ini --apply
```
The manifest is the source of truth for the base fields and the combat
bonuses/category/anims alike; re-running it regenerates `vitur.obj` from
scratch (that file is a build output, the same way `dclaws.obj` is for the
claws pack).

## Animations

**The item's own OSRS animations are ported, not substituted.**

| role | seq | name | source |
| --- | --- | --- | --- |
| stance | 8057 | `scythe_of_vitur_ready` | **ported** — 12 frames, 240 cycles = 8.00 ticks, looping |
| slash / crush | 8056 | `scythe_of_vitur_attack` | **ported** — 22 frames, 77 cycles = 2.57 ticks |
| defence | 435 | `human_scythe_block` | native — already in rev 254 at the same id |

The names come from `cache.osrs230` because **osrs239 carries no seq debug
names**, while the export itself reads osrs239. That split is only safe
because the ids were re-verified in the export cache rather than assumed:
`find_named --rev osrs239 cache.osrs239 --seq 8056/8057` returns
byte-identical frame lists and durations. Never copy an id between caches
without that check.

`human_scythe_block` is native and is *not* re-exported: rev 254 already
ships it, at the same id (435) the source cache uses. It is not
`human_scythe_spin` — that is the defensive attack *style's* swing, which
`combat.rs2`'s existing `weapon_scythe` case plays on its own, and putting it
in `defend_anim` made a block play an attack.

### The tile graphic

The sweep drawn on the target's tile is **four assets, one per compass
direction** — which is the entire reason it appears to vary between swings.
Nothing is choosing at random; the swing direction picks the graphic.

| spotanim | name | model |
| --- | --- | --- |
| 506 | `dragon_halberd_special_north_red` | 4004 |
| 478 | `dragon_halberd_special_south_red` | 4005 |
| 1172 | `dragon_halberd_special_east_red` | 4003 |
| 1231 | `dragon_halberd_special_west_red` | 4006 |

All four share seq 1204 (`sp_d_halberd_glow`), which is ported with them.
They keep their source names rather than being renamed to something
scythe-ish: they genuinely *are* the dragon halberd special's graphics, reused
by this weapon in the source game, and renaming would both hide that and
collide the day someone ports the halberd.

`[proc,scythe_sweep_gfx]` picks between them off the same dx/dz the cleave
already computes, so the direction costs nothing extra to work out.

**The spotanim models carry their own rig** (labels 0–12 over 24 vertices, on
framemap 899) and must not be touched by the player-rig retarget —
`RIGGING_OSRS_RS2.md`'s documented way to make a graphic fly apart. That is
what `rig_framemaps = 0` in the manifest is for. Verified after export: the
ported models' labels are byte-identical to the source's, and
`vitur_animset_899.anim` still has 13 transforms with a highest label of 12,
i.e. its own joints, not player joints.

## Mechanics

Not a special attack — no spec bar, no energy cost. Every normal hit with
this specific item does this, which is why the gate in `player_melee.rs2` is
on the item (`$weapon = scythe_of_vitur`) and not on `weapon_scythe`: the
tree's other scythes, sharing that category, hit once.

The primary target's hit is the only accuracy/damage roll. The tile directly
behind it, continuing the swing's own direction (attacker -> target,
extended one more tile), takes 50% of that damage; the tile behind *that* one
takes 25%. Both floor. A miss on the primary — or a hit that rolls to exactly
0 — reaches no further, by an explicit `$damage > 0` guard rather than by
accident.

Direction comes from attacker/target coordinates, not a facing byte: melee is
orthogonal-only, so exactly one of dx/dz is ±1 at the moment of the swing, and
continuing that offset twice is the line already being swung along.
`npc_findallany` is unfiltered by npc type on purpose — whatever is standing
on the tile takes the splash, the same as the live item.

Experience is paid for the cleave hits too (capped to the target's remaining
hitpoints, same as the primary), which matches the live item and is part of
why it is a popular training weapon — dropping that would be a silent nerf,
not a simplification.

**Deliberately not ported**: the charge/degrade system. `configs/all.obj`
(the 3draster osrs239-content tree) shows a `scythe_of_vitur_uncharged`
sibling item and `ifop3=Check` / `ifop4=Uncharge` inventory options with no
`Charge` option among them — real cache data, so the live item probably does
have some charge mechanic, but this pack does not implement it. `vitur.obj`
still carries the two inert options (`iop3=Check`, `iop4=Uncharge`) because
the exporter copies them straight off the cache record; clicking either does
nothing right now. Wiring that up is a separate, self-contained follow-up.

**Deliberately not restricted**: nothing stops this cleaving in PvP. The real
item is banned from PvP-enabled areas specifically because of this mechanic
against multiple players — but LostCity's player-vs-player melee runs through
a different script than the player-vs-npc path this hooks into
(`[label,player_melee_attack]` reads `npc_stat`/`npc_param`/`npc_queue`
throughout, so it cannot be the PvP path), so the cleave simply never fires in
PvP as a consequence of where it is hooked, not because of an explicit
restriction. Worth stating rather than leaving implicit, since the next
person to touch PvP melee should know this item's correctness depends on it.

## Model — what was verified and what was not

The wield model (both genders, 390 vertices) carries exactly one vertex label,
uniformly 50 in the source cache. That is OSRS's equipment-grip label, not a
body joint, so `RIGGING_OSRS_RS2.md`'s identikit correspondence table does not
cover it — that table is derived from the bare body, which has no vertices
there.

It is retagged to rev 254's **66**, that era's own held-weapon joint, and the
evidence is structural rather than by analogy. In OSRS framemap 0, label 50
has its own dedicated pivot (`[87] origin labels: 50`) and rides the same
wrist/forearm transforms — `[34]`, `[35]`, `[47]`, `[48]` — that in rev 254's
`anim_80.anim` drive 66 and only 66.

`[export:rig_map]` maps `50 = 66` to match, and that pairing is what makes
both eras' animations work on one model: the ported sequences move the weapon
because their label-50 transforms are renumbered to 66, and rev 254's native
walk/run/idle move it because they already drive 66.

After export the retargeted animset lines up with the native rig transform for
transform, which is the strongest structural confirmation available here:

| transform | rev 254 native `anim_80` | ported, retargeted |
| --- | --- | --- |
| `[34]`/`[35]` | `17 66 70` | `254 17 66` |
| `[47]`/`[48]` | `66` | `254 66` |
| `[87]` origin | — | `66` |

Identical apart from labels parked on 254 (which no rev-254 model uses). Also
checked: all 390 vertices carry 66, no transform names a label twice (the
duplicate-collapse trap that silently multiplies a rotation), and `[5] origin`
lands on joint 18 (pelvis) where the native rig uses 19 — the same joint, and
the signature the rigging guide gives for a correct retarget.

Two rejected label choices, both of which half-work, recorded because the
failure modes are not symmetrical:

- **17** (the left hand — what `dragon_claws.ini` uses for this same source
  label). The weapon follows the hand, but the source animation's own weapon
  motion, everything transform `[87]` exists to pivot, is thrown away.
- **66 in the model but not in the rig map** — the state this port was in
  before the animations were ported. Native anims move it; the ported ones
  never touch it, so the weapon hangs motionless in mid-air through its own
  attack.

Still not checked: no live client this session, so nothing was confirmed by
eye — position, orientation and how the swing reads in motion are unverified.
