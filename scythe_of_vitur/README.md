# Scythe of Vitur — backport from OSRS to LostCity rev 254

A Theatre of Blood weapon (OSRS obj 22325), backported straight from
`cache.osrs239` with `3draster/3rd/rscache/tools/port_lostcity` and its
manifest `port_lostcity/scythe_of_vitur.ini`. See `ghrazi_rapier/README.md`
(same session, same method) for the companion item.

## No LostCity reference

This content tree preserves 7 September 2004, fifteen years before Theatre of
Blood existed. `grep -ril vitur LostCity_Server/content` finds nothing but
this port's own files. The one thing the tree already had is the generic
`weapon_scythe` category — a style table (`combat.dbrow`) and the defensive
spin case in `skill_combat/scripts/combat.rs2` — which this item reuses for
its base stats, but which says nothing about hitting more than one target.
That is the whole of what is "content there" for this item; the cleave itself
is authored fresh.

To redo or re-derive this export: from the `3draster` repo root,
```
./3rd/rscache/tools/port_lostcity/port_lostcity \
  --manifest 3rd/rscache/tools/port_lostcity/scythe_of_vitur.ini --apply
```
The manifest is the source of truth for the base fields and the combat
bonuses/category/anims alike; re-running it regenerates `vitur.obj` from
scratch (that file is a build output, the same way `dclaws.obj` is for the
claws pack).

## Mechanics

Not a special attack — no spec bar, no energy cost. Every normal hit with
this specific item does this, which is why the gate in `player_melee.rs2` is
on the item (`$weapon = scythe_of_vitur`) and not on `weapon_scythe`: the
tree's other scythes, sharing that category, hit once.

The primary target's hit is the only accuracy/damage roll. The tile directly
behind it, continuing the swing's own direction (attacker -> target,
extended one more tile), takes 50% of that damage; the tile behind *that* one
takes 25%. Both floor. A miss on the primary — or a hit that rolls to exactly
0 — reaches no further, by an explicit `$damage > 0` guard rather than by
accident.

Direction comes from attacker/target coordinates, not a facing byte: melee is
orthogonal-only, so exactly one of dx/dz is ±1 at the moment of the swing, and
continuing that offset twice is the line already being swung along.
`npc_findallany` is unfiltered by npc type on purpose — whatever is standing
on the tile takes the splash, the same as the live item.

Experience is paid for the cleave hits too (capped to the target's remaining
hitpoints, same as the primary), which matches the live item and is part of
why it is a popular training weapon — dropping that would be a silent nerf,
not a simplification.

**Deliberately not ported**: the charge/degrade system. `configs/all.obj`
(the 3draster osrs239-content tree) shows a `scythe_of_vitur_uncharged`
sibling item and `ifop3=Check` / `ifop4=Uncharge` inventory options with no
`Charge` option among them — real cache data, so the live item probably does
have some charge mechanic, but this pack does not implement it. `vitur.obj`
still carries the two inert options (`iop3=Check`, `iop4=Uncharge`) because
the exporter copies them straight off the cache record; clicking either does
nothing right now. Wiring that up is a separate, self-contained follow-up.

**Deliberately not restricted**: nothing stops this cleaving in PvP. The real
item is banned from PvP-enabled areas specifically because of this mechanic
against multiple players — but LostCity's player-vs-player melee runs through
a different script than the player-vs-npc path this hooks into
(`[label,player_melee_attack]` reads `npc_stat`/`npc_param`/`npc_queue`
throughout, so it cannot be the PvP path), so the cleave simply never fires in
PvP as a consequence of where it is hooked, not because of an explicit
restriction. Worth stating rather than leaving implicit, since the next
person to touch PvP melee should know this item's correctness depends on it.

## Model — what was verified and what was not

The wield model (both genders, 390 vertices) carries exactly one vertex
label, uniformly. In the source OSRS cache that label is 50; it does **not**
correspond to anything in `RIGGING_OSRS_RS2.md`'s identikit correspondence
table, because that table is derived from the bare body model and equipment
wield models turn out to use a separate, equipment-only part of the same
label space — confirmed by checking a real, shipping rev-254 item (see
below), not by trying the identikit table and it happening to look plausible.

This item is two-handed (`wearpos=righthand`, `wearpos2=lefthand`), so the
closest native rev-254 analogue by grip shape is a spear, not a one-handed
sword. `skill_combat/configs/melee/spears.obj`'s `manwear=model_540_obj_wear`
is, measured with this session's own extension to `find_named`
(`--model`/`--ob2` now print a `vertex labels` line), 100% label 17. The
manifest maps `50 = 17` on that basis.

Structurally confirmed live rather than assumed inert:
`find_named --dat1-anim <content>/models/anim_80.anim` shows label 17 driving
transforms `[33]`/`[34]`/`[35]` (a dedicated hand-adjacent rotation) and
riding along in the shoulder sweep at `[29]`/`[30]`, so this is not an
unaddressed number sitting still.

**What was not checked**: no live LostCity client was available this session,
so nothing here was confirmed by actually watching the weapon swing. A single
uniform vertex label cannot *stretch* the way a multi-label model can (that
failure mode needs mismatched per-label deformation, and this model has only
one label to deform), so the two live failure modes from
`RIGGING_OSRS_RS2.md` that remain possible are: the label is wrong
category-wise (checked, by direct analogy to a shipping item with the same
grip shape) or the model hangs at a visually odd offset from the hand (not
checked — would need an in-client screenshot). If the weapon looks
detached or mispositioned in a real client, that is the thing to check first.
